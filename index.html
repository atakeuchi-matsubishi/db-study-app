データベースとは何か

データベースの概念とDBMSの役割を理解しましょう。

データベースの定義

データベースとは、複数の人で共有・再利用しやすいよう一定の形式で管理されたデータの集合です。紙の電話帳や宿泊者名簿もデータベースですが、通常はコンピュータ上のものを指します。

身近な例
  • Amazon：数億件の注文・商品・顧客情報を同時に複数のスタッフ・システムが参照・更新している
  • 病院の電子カルテ：医師・看護師・薬剤師が同じ患者の診療記録を同時に参照し、それぞれ異なる情報を書き込む
  • Suica・ICカード：全国のどの改札でも残高を読み書きできるのはDBが一元管理しているから
  • スマホの連絡先アプリ：自分だけが使う小さなDBの一例（共有性はないが構造化されたデータ）
ポイント：「複数人が大量データを同時に使う」場面でDBが真価を発揮します。1人だけのメモならDBは不要です。

DBMSとは

DBMS（データベース管理システム）はデータ操作の細かい制御をアプリの代わりに担うミドルウェアです。

身近な例
  • レストランのホールスタッフ：お客様（アプリ）は「ハンバーグ定食ください」と言うだけ。厨房（DBMS）がどの順番で何を調理するかを管理する。アプリ側は細かいデータ管理を知らなくていい。
  • 代表例：MySQL、PostgreSQL（Supabaseで使用）、BigQuery

データベースの種類

種類説明現在
関係型（RDB）表形式。SQLで操作。現在の主流✅ 主流
階層型ツリー構造❌ ほぼ廃止
ネットワーク型グラフ構造❌ ほぼ廃止

Chapter 3

E-R図とエンティティ

概念データモデルの表記法と、エンティティ・属性の概念を学びます。

E-R図とは

E-R図は実世界をエンティティ（実体）とリレーションシップ（関係）でモデル化した図です。

身近な例 — Instagramで考える
  • エンティティ：ユーザー、投稿、コメント、ハッシュタグ
  • 属性：ユーザー名、フォロワー数、投稿日時、本文
  • リレーション：「投稿する」（ユーザー→投稿）、「コメントする」（ユーザー→コメント）、「タグ付けする」（投稿→ハッシュタグ）

エンティティ・インスタンスとは

エンティティは「見たいこと・知りたいこと」を概念化したもの。実態がないもの（予約・注文・イベント）でもエンティティになります。

エンティティ＝属性の集まり（設計上の「型」）
インスタンス＝属性値の集まり（実際の1行データ）

例：「顧客」エンティティの属性＝顧客ID・名前・メール
インスタンス例＝「C001 / 田中花子 / hanako@example.com」
身近な例 — 学校で考える
  • エンティティ：生徒、授業、教師、教室、成績
  • インスタンス例（生徒）：「S001 / 山田太郎 / 3年A組」が1件のインスタンス
  • 「成績」は実態がないがエンティティになれる（生徒ID・科目ID・点数・評価の集まり）

Chapter 4

主キー・外部キー・NULL

インスタンスを一意に識別する「キー」とNULLの意味を理解します。

主キー（Primary Key）

インスタンスを一意に識別できる極小の属性（または属性の組）を主キーと言います。

主キーの制約：
① 一意性制約：同じ値が2件以上存在できない
② 非NULL制約：NULLを許可しない
身近な例
  • マイナンバー：国民1人に1つだけ割り当てられる番号。氏名は同姓同名があるためNGだが、マイナンバーは一意。主キーの典型例
  • 学籍番号：同じ学校内で重複しない。「田中くん」は3人いてもS2024-001は1人だけ
  • 注文番号：Amazonの注文番号は重複しない。購入者・商品が同じでも注文ごとに別の番号が付く
  • 複合キーの例：「時間割」テーブルは（曜日・時限・教室）の組み合わせで一意になる

外部キー（Foreign Key）

別のエンティティの主キーを参照する属性が外部キー（FK）です。テーブル間をつなぐ「橋」の役割を担います。

身近な例 — 注文と顧客をつなぐ
  • 注文テーブルに「顧客ID」列を持たせることで、その注文が誰のものかを特定できる
  • 注文テーブルの「顧客ID」＝外部キー（顧客テーブルの主キーを参照）
  • イメージ：注文書に書かれた「会員番号」で、顧客名簿から氏名・住所を引っ張ってくる

NULLとは

身近な例 — NULLは「値なし」≠ 0 ≠ 空文字
  • 「まだ決まっていないNULL」：配送日未定の注文。いずれ日付が入るが、今はNULL
  • 「論理的にありえないNULL」：独身者の「配偶者名」欄。絶対に値が入らない
  • 空文字との違い：アンケートで「名前を入力しなかった（NULL）」と「わざと空白を入力した（空文字）」は意味が違う
  • 0との違い：テスト0点（値あり）と欠席で採点なし（NULL）は別物

多重度とリレーションシップの種類

エンティティ間の「数の対応関係」とN:Mの解消方法を学びます。

リレーションシップの種類

種類頻度身近な例
1 対 1△ 珍しい社員 ↔ 社員証、日本人 ↔ マイナンバー
1 対 多✅ 最多顧客 → 注文複数件、ブログ筆者 → 記事複数本
多 対 多⚠ 要解消学生 ↔ 科目、商品 ↔ 注文
身近な例 — ECサイトで考える
  • 顧客 → 注文（1:N）：1人の顧客が何度でも注文できる。注文は必ず1人の顧客に紐づく
  • 注文 ↔ 商品（N:M）：1つの注文に複数商品が入り、1つの商品が複数注文に含まれる → そのまま格納できないので「注文明細」という連関エンティティを作る
  • 図書館（著者 ↔ 本 → N:M）：1人の著者が複数の本を書き、1冊に複数著者が関わることもある → 「執筆」という連関エンティティで解消

N:Mの解消：連関エンティティ

N:Mのままではテーブルに格納できません。連関エンティティを追加して1:N×2に分解します。

学生 ↔ 科目（N:M）→ 受講テーブルを追加
学生（1）→ 受講（N）← 科目（1）

連関エンティティの主キー = 両方の主キーを組み合わせた複合キー
身近な例 — Spotifyで考える
  • プレイリスト ↔ 楽曲（N:M）→「プレイリスト楽曲」テーブルで解消
  • プレイリスト楽曲テーブル：（プレイリストID, 楽曲ID, 追加日時, 並び順）
  • 主キー = プレイリストID ＋ 楽曲ID の複合キー

強エンティティと弱エンティティ

エンティティの独立性による分類と自己参照を学びます。

強エンティティ vs 弱エンティティ

種類定義身近な例
強エンティティ独立して存在できる顧客、商品、社員、部署
弱エンティティ対応する親エンティティがないと存在できない注文明細、売上明細、請求明細
身近な例 — Amazonで考える
  • 注文（強）→ 注文明細（弱）：「注文A」が削除されたら「注文A-商品1・商品2」という明細も存在できない
  • 見分け方のコツ：「○○明細」は弱エンティティの典型
  • ホテルの例：「部屋」は独立して存在できる（強）。「予約」は部屋と宿泊客がいて初めて意味をなす（弱）という見方もできる
  • 請求書（強）→ 請求明細（弱）：請求書がなければ明細行は存在しない

自己参照（ループ構造）

同じエンティティの主キーを外部キーに設定するパターンです。

身近な例
  • 社員テーブルの上司：「上司ID」= 同じ社員テーブルの社員IDを参照。部長も課長も一般社員も同じテーブルに入り、上司→部下の階層を表現
  • カテゴリの親子：「カテゴリ」テーブルで「親カテゴリID」が同じテーブルを参照。「家電 → テレビ → 4Kテレビ」のような入れ子構造
  • SNSのリプライ：「投稿」テーブルの「返信先投稿ID」が同テーブルの投稿IDを参照

Chapter 7

スーパータイプとサブタイプ

エンティティの継承関係と排他的・共存的サブタイプを学びます。

スーパータイプ・サブタイプとは

エンティティを上位（スーパータイプ）と下位（サブタイプ）に分ける継承構造です。

身近な例 — 会員制サービスで考える
  • スーパータイプ「会員」：全会員共通の属性（会員ID・氏名・登録日）を持つ
  • サブタイプ「個人会員」：生年月日・趣味など個人特有の属性を追加
  • サブタイプ「法人会員」：法人番号・担当者名など法人特有の属性を追加
  • E-R図では三角形のマークでスーパー↔サブをつなぐ

排他的 vs 共存的サブタイプ

種類意味身近な例
排他的いずれか1つのサブタイプにしか属せない個人会員か法人会員のどちらか一方のみ
共存的複数のサブタイプに同時に属せる取引先が仕入先かつ得意先にもなれる
身近な例 — 判断のコツ
  • 兼務・兼任があれば共存的：「社員は正社員か契約社員か」→ 両方兼務はありえない → 排他的
  • 取引先：仕入れもするし売りもする取引先が存在する → 共存的
  • 血液型で考える：A型かつB型は存在しない → 排他的
  • 資格保有で考える：1人が「簿記1級」と「宅建」を同時に持てる → 共存的
共存的が排他的に優先される：1人でも両方に属するケースがあれば共存的。
記述がないときは常識で判断：「法人かつ個人」はありえない → 排他的

完全・不完全サブタイプ

身近な例
  • 完全なサブタイプ：「動物園の動物」がサブタイプ「哺乳類・鳥類・爬虫類」のいずれかに必ず入る場合
  • 不完全なサブタイプ：「商品区分」に「その他」がある場合。どのサブタイプにも分類できない商品が存在する
  • 見分け方：サブタイプ識別子（○○区分）の値に「その他」があれば不完全
